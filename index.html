01 · Abstract

A model should earn its complexity — and its numbers should survive an audit.

This study investigates whether historical search-performance signals can support content prioritization for potential refresh review. A transparent rule-based baseline was developed first, followed by Decision Tree and Random Forest models trained on an audited, leakage-free feature set. A self-review of the pipeline caught two issues after initial results looked implausibly strong: an unshuffled data sample that collapsed the working set to a handful of clients, and a proxy target built from the same two fields the model was also given as inputs. Both were fixed and the pipeline was re-run. On the corrected, grouped, leakage-free evaluation, the transparent baseline still leads on F1 (83.7%) against class-weighted Decision Tree (35.7%), Random Forest (37.0%), and a probability-threshold-tuned Random Forest (40.7%) — though the weighted/tuned models do recover full recall, at a real cost to precision. The resulting action queue remains directional decision-support for human review, not evidence that a refresh will cause improved search performance.

02 · Research question

Turn a large content inventory into a review order.

The selected capstone lane is Refresh / Content Opportunity Scoring.

The practical decision is simple: which content items should a reviewer inspect first? The system is intentionally not asked to decide whether a page must be refreshed, rewritten, deleted, or expected to gain traffic.

04 · Methodology

Baseline first. Model second. Audit everything, including the audit.

Proxy target

Rows where average position is above 20 and clicks are below 5. This is a constructed proxy, not a human-verified "needs refresh" label.

Models compared

Week-4 baseline rule, plain Decision Tree (max_depth=5), class-weighted Decision Tree, class-weighted Random Forest, and a Random Forest with its decision threshold tuned to maximize F1.

Grouped validation

GroupShuffleSplit holds out 20% of client groups (55 train clients / 14 test clients, 0 overlap). A hard assertion blocks the run if either side falls below 5 clients.

Leakage control

The two variables that directly construct the proxy target — gsc_clicks and gsc_avg_position — are excluded from every model's feature set by construction: a single variable defines them once and both the target formula and the feature filter read from it, so the two can't drift out of sync.

Why the audit matters: allowing a model to see variables that directly define its target can make performance look stronger than the underlying predictive evidence — an earlier run of this exact pipeline scored 100% accuracy for this reason before the bug was caught and fixed.
05 · Audit trail

What was wrong, and how it was found.

In the interest of an honest, reproducible capstone, the two issues that inflated earlier results are documented here rather than quietly dropped.

IssueSymptomFix
Target leakagegsc_clicks / gsc_avg_position were used to build the target and left in the feature set — Decision Tree scored a suspicious 100% accuracy, with feature importance showing gsc_avg_position at 1.0 and every other feature at 0.0.Both fields are now excluded from the feature set by construction, driven from the same variable that defines the target formula.
Unshuffled sampling.select(range(10000)) without shuffling drew the sample from the front of storage order, collapsing it to ~3 unique clients — the grouped test set ended up with a single client, making "grouped validation" close to meaningless.Data is now shuffled (seed=42) before sampling, and the pipeline asserts a minimum client count (≥20 in-sample, ≥5 per split side) before any metric is trusted.
Miscalibrated leakage trip-wireA quantitative single-feature leakage check flagged every feature as "suspicious" at once — turned out to be an artifact of class imbalance (a depth-3 tree defaults to predicting the majority class for any feature, matching the 90.2% base rate exactly).The check now compares each feature against the majority-class baseline and additionally requires non-trivial recall before flagging a feature as leakage.

Reading the pattern

An unweighted Decision Tree simply predicted the majority class for every row, producing 0% recall despite 96% accuracy — a textbook symptom of an unaddressed 90/10 class imbalance, not a leakage bug. Adding class_weight="balanced", and separately tuning the classification threshold on Random Forest's predicted probabilities, both fully recovered recall to 100% — every actual refresh-candidate page was caught. The cost was precision: only ~23–26% of flagged pages were true positives, versus 100% for the simple rule. On F1, which balances both, the rule-based baseline remains ahead.

Interpretation: the audited features carry real but limited independent signal once gsc_clicks/gsc_avg_position are removed — enough to fully recover the minority class with the right weighting, not enough to do so without a heavy precision cost. Which model to prefer depends on whether missing a refresh candidate (favor the weighted models) or wasting reviewer time on false alarms (favor the baseline) is the costlier mistake for the team.
07 · Limitations

What this study does — and does not — show.

Supported

  • The baseline and four model variants can be compared on the same grouped, leakage-audited test set.
  • Class weighting and threshold tuning materially change the precision/recall trade-off versus an unweighted tree.
  • The queue can be used as directional review prioritization.
  • Leakage and sampling risks were caught, documented, and corrected rather than silently fixed.

Not supported

  • A claim that refreshing content will cause better rankings.
  • A claim about Google's ranking algorithm.
  • A claim that the queue predicts refresh success.
  • Automatic publishing, rewriting, deletion, or pruning.
Honest framing: words such as observed, measured, directional, associated, and decision-support are preferred throughout this artifact.

Human review checklist

  1. Confirm search demand and data quality.
  2. Check current intent and content fit.
  3. Consider seasonality and recent editorial changes.
  4. Assess business importance.
  5. Only then decide whether a refresh is appropriate.
No-go list: do not automatically publish, rewrite, delete, prune, or claim guaranteed performance improvement from a queue score.

A paper backed by a corrected notebook trail.

  • w05_model.ipynb — target-defining fields excluded from features programmatically
  • w06_validation_audit.ipynb — shuffled sampling, client-count guard, corrected quantitative leakage trip-wire
  • w07_action_playbook.ipynb — action playbook (already shuffled correctly)
  • capstone.ipynb — final workflow: shuffled sample (69 clients), leakage-free features, class-weighted models, threshold tuning
